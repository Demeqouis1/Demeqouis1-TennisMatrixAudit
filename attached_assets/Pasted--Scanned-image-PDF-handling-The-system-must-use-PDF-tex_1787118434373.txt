    Scanned/image PDF handling. The system must use PDF text extraction first, then page-image/vision extraction when text is missing or corrupted. It must confirm every page was processed and never treat an image-only page as blank.
* Separate Matrix calibration from Audit-color performance. Your evolving 183 calibration should continue grading the original Matrix WP buckets exactly as specified, but the system should also maintain a separate learning ledger for Double Green / Green / Yellow / Red outcomes. That lets you determine whether Greens are actually outperforming Yellows and whether thresholds need tightening. Never mix that ledger into the 183 bucket denominator.
* Grade the Matrix pick and final audit pick separately. For every completed match store: matrix_prediction_result, independent_audit_result, and final_selection_result. Otherwise you won’t know whether the Matrix was wrong, the independent audit corrected it, or the audit introduced the mistake.
* False-Green / successful-downgrade autopsy. Every Green/Double-Green loss should automatically trigger a post-result review using pre-match evidence only to classify why the audit failed: rapid riser missed, stale rating, surface mispricing, market contradiction, opponent ceiling, injury uncertainty, matchup collision, etc. Every successful Red/Yellow downgrade should be logged too. Those findings should inform future rule revisions but must never retroactively alter the original audit.
* No future leakage in post-match learning. Post-match score, injury discovered during the match, live stats, or performance cannot be used to claim the pre-match audit “should have known” something unless that information was publicly available before first serve.
* Timezone and first-serve normalization. Store tournament-local time, UTC time, scheduled time, actual first serve, research lock, and result time. Daylight-saving/timezone errors must not cause post-start information to enter a pre-match audit.
* Source outage and rate-limit handling. Add retries, exponential backoff, source-health monitoring, quotas, and fallback-source logic. A temporarily unavailable website should create a source failure record, not cause the system to assume the underlying metric is unavailable forever.
* Source terms/compliance. Only retrieve data in ways permitted by the source. Support APIs, licensed feeds, approved scraping where allowed, and manual data entry. The system should not be architected around brittle or prohibited scraping.
* Research completeness by evidence family. Don’t only report “591/591 metrics.” Also show whether every critical evidence family has adequate coverage: present strength, surface form, serve/return, opponent quality, availability, market, recent ceiling, etc. Hundreds of unavailable supplemental metrics should not disguise a missing critical family.
* Independent probability construction must be explicit. Store the exact method/formula/version used to turn independent evidence into the independent probability range. Otherwise an AI could correctly execute all the rules but still invent 72–78% at the end.
* Probability provenance. Every number in the final board—Matrix WP, independent range, calibrated range, Verified Win Rate, audit confidence—must be traceable back to its calculation and inputs.
* Manual overrides must never erase computed results. If you manually change a surface, result, rule mapping, metric, or classification, preserve both SYSTEM VALUE and MANUAL OVERRIDE, who changed it, when, and why.
* Permissions. Separate ordinary user actions from administrator actions. Replacing audits, modifying calibration history, changing result grading, blacklisting sources, and overriding rule logic should require admin permission.
* Backups and exports. Provide export/backup for rules, source definitions, calibration ledger, audit history, raw parsed summaries, and generated reports so the system is not dependent on one database instance.
* PDF template versioning and validation. Store the PDF template version, automatically verify that every ranked match appears exactly once, row colors match the correct active calibration bucket, rankings follow Audit Color first → Verified Win Rate second, and totals in the header equal the rows in the board.
* Batch integrity check. Before calling a slate finished, automatically reconcile: number of matches uploaded = canonical matches identified = matches represented on the board. Duplicates should be merged and unresolved/missing matches explicitly accounted for.
* No automatic downgrade because something is unavailable. Missing data must be treated according to the active audit’s actual rules. UNAVAILABLE should not secretly count against either player unless the audit explicitly defines a missing-data penalty.
* Immutable formulas/rule versions per audit run. If a reconstruction formula changes tomorrow, yesterday’s audit must continue pointing to yesterday’s formula.
* Reason codes for every blocking state. INCOMPLETE alone isn’t enough. Require machine-readable reasons such as SURFACE_CONFLICT, PLAYER_ID_UNRESOLVED, VERIFICATION_RULE_42_UNMAPPED, CRITICAL_SOURCE_STALE.
* Do not confuse historical success with current probability. The 78.9% Verified Win Rate for the 65–69 Matrix bucket is a historical bucket result—not automatically the current player’s 78.9% chance of winning. It should rank/calibrate exactly as you specify without being mislabeled as the match’s independent probability.

The most important addition is probably the separate three-way result tracking:

MATRIX RESULT
INDEPENDENT AUDIT RESULT
FINAL SELECTION RESULT

That will let you audit the auditor. If the Matrix picked Player 1, the independent audit picked Player 2, and Player 2 won, you’ll know the audit successfully corrected the Matrix. If the Matrix was right and the audit flipped away from it, you’ll know the audit introduced the error. Without that separation, your learning data can blur the exact failure mechanism.
